# UX-001 — Primary and accent color review

Reviewed 2026-11-05–06 against commit `cf0fb87`, Qt 6.12.0 MSVC 2022 x64, and the
ten accepted UI-013 backgrounds. This is an analysis record; application code,
palette defaults and settings are unchanged. User clarification: the vivid shade
shift in `Theme.qml` is intentional because the standard palette looks bleak.

**Recommendation: retain that shift and the two user-selected color families.**
It produces the intended stronger accent colors using Qt's existing Material
palette ramps. The problems found concern foreground/background pairings and
using a bright fill color directly as small text, rather than a need to make the
whole app muted. Proposed corrections are separate UI-025/UI-026 tickets.

## Roles in the current app

| Area | Actual role and binding | Assessment |
| --- | --- | --- |
| `app/main.qml`, `Theme.qml` | Window receives resolved `Theme.primaryColor()` and `Theme.accentColor()`; theme, primary/accent and normal foreground/background propagate | A clear central choice. Keep it |
| `Weekdays.qml`, instantiated by `ShopView.qml` above the list/pull area | Primary colors the current day's name and number-circle fill; number uses `Material.primaryHighlightedTextColor` | Distinguishes today with both position and shape. Name and filled-circle foreground need different contrast treatment |
| Three theme buttons in `View.qml`, using `IconButton.qml` | Accent fills the selected button; inherited Qt highlighted foreground colors its icon; caption remains normal foreground | Selection is also identified by the caption/icon. Several fills make the icon faint |
| `ComboBox.qml`, `ColorComboBox.qml`, `Slider.qml`, `GroupBox.qml` | Accent marks focused borders, selected popup text, active slider track and thumb | Roles are coherent. Bright accent used as ink or a thin focus indicator needs a readable variant/outline |
| `UndoBar.qml` | Opaque accent countdown fill; fixed normal-theme text/icon; inverse-theme surface at 20% opacity after the fill recedes | Preserve the accepted animation, whole-bar action and transparency. Current normal-theme foreground does not contrast with every accent fill |
| `AboutDialog.qml` | Accent marks the selected tab text/underline | Same accent-ink contrast concern; no need to change the reader structure |
| `Pulley.qml`, `TextDelegate.qml`, `Icon.qml` | Accent signals a pull threshold, long press, or pressed icon | Appropriate feedback role; detailed custom component/state audit remains UX-003 |
| Shopping rows, editor, drawer, safe areas and ordinary labels | Neutral resolved Material foreground/background, with deliberate opacity and inverse checked/editor surfaces | These mostly do not depend on the selected primary/accent. Keep that separation |
| Red/green swipe feedback | Fixed action colors rather than the user-selected primary/accent | Meaning and alternatives remain UX-002; no replacement proposed here |

`Material.primaryTextColor` is a neutral text role, not the selected primary hue.
Likewise, the tested Qt `primaryHighlightedTextColor` stays white in these
highlighted controls; its name does not make it a contrast-aware M3 `onPrimary`.
There is no production ToolBar, so Qt's usual primary toolbar treatment is not
the app's main primary-color consumer. Android system-bar icon brightness follows
the window's neutral surface in `main.cpp`, not an accent or primary hue.

## What the shade shift actually does

The native probe compares the app with a stock Qt Material RoundButton receiving
typed predefined color enums. It does not compare the app against colors copied
from a web screenshot.

| Role | Qt predefined color, Light / Dark | QShopper, Light / Dark |
| --- | --- | --- |
| Primary | Shade500 / Shade500 | Shade500 / Shade200 |
| Chromatic accent (16 families) | Shade500 / Shade200 | ShadeA400 / ShadeA200 |
| Brown, Grey, BlueGrey accent | Shade500 / Shade200 | Shade500 / Shade200 |

Examples measured from Qt 6.12:

| Color | Qt Light → QShopper Light | Qt Dark → QShopper Dark |
| --- | --- | --- |
| Green accent | `#4caf50` → `#00e676` | `#a5d6a7` → `#69f0ae` |
| Purple accent | `#9c27b0` → `#d500f9` | `#ce93d8` → `#e040fb` |
| Indigo primary | `#3f51b5` → `#3f51b5` | `#3f51b5` → `#9fa8da` |

This is palette-shade selection, not an arbitrary color-space offset. The A ramps
give the desired vivid accents, but do not preserve exactly the same hue or
brightness for every family: Green becomes noticeably more mint-like. That is a
reasonable intentional choice, not an error. The neutral-family exception avoids
using absent A ramps. The lighter primary in Dark helps the current-day name
stand out against its dark translucent surface; reverting it globally would also
change that useful foreground behavior. The final default-pair probe measures
2.40:1 with Qt's unshifted Indigo versus 7.14:1 with the app's lighter Indigo for
that name, while the circle's white number needs separate treatment.

`accentColorLighter()` selects A200 in Light/A100 in Dark, with the same neutral
fallback, but has no production caller. It does not affect the current appearance.
The visible picker swatches match the resolved window primary/accent in all 19
families and all four tested theme modes. Picker activation owns the selection;
the probe explicitly synchronizes indices when changing settings programmatically.

## Comparison with Android/Material guidance

Android's [color guidance](https://developer.android.com/design/ui/mobile/guides/styles/color)
emphasizes consistent roles, paired foreground/container contrast, separate
Light/Dark assignments and restrained emphasis. It allows expressive/custom static
schemes. These support retaining QShopper's vivid treatment while correcting the
specific pairings. Automatically extracting a different palette from each of ten
slideshow images would make action colors less predictable; that is not recommended.

[Material 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3)
uses explicit tonal roles such as primary/onPrimary and primaryContainer. Qt's
[Material style](https://doc.qt.io/qt-6/qtquickcontrols-material.html) exposes
primary/accent/foreground/background and is a cross-platform implementation.
QShopper's accent currently performs many jobs that M3 would call primary
interaction emphasis. The naming difference is not itself a defect or a reason
to migrate frameworks, rename the user's settings, or add a complete token system.

Use [Android's contrast guidance](https://support.google.com/accessibility/android/answer/7158390?hl=en)
to evaluate apparent colors after composition: normally 4.5:1 for small text and
3:1 for large text. [WCAG's non-text contrast explanation](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
uses 3:1 for meaningful controls/state cues; it does not require every decorative
border to meet that ratio. These are review targets, not a claim of whole-app
accessibility certification. Contrast measures use the underlying foreground
color with its alpha composited over the rendered background, not antialiased
edge pixels; see [contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

## Rendered findings

The native Windows probe uses production Weekdays, IconButton, ColorComboBox
and UndoBar components, with an isolated comparison panel. It records 19 same-family palette
sweeps plus four mixed primary/accent pairs in Light, Dark, System→Light and
System→Dark: 92 palette records. The typed Qt reference preserves enum types;
production popup settings mirror the window's palette. Early probe-only typing
and popup-context issues were corrected before retaining measurements. The final
probe also explicitly qualifies QShopper's Menu and Slider rather than the
overlapping Qt Material types; comparison-panel fields from earlier native runs
are excluded from the retained native data.

Representative measured contrast ratios:

| Theme and primary/accent | Day number on primary circle | Selected icon on accent fill | Undo text on full fill | Selected Accent-popup label on highlighted row |
| --- | ---: | ---: | ---: | ---: |
| Light, Indigo/Green defaults | 6.87 | 1.67 | 10.49 | 1.28 |
| Dark, Indigo/Green defaults | 2.31 | 1.43 | 1.43 | 7.95 |
| Light, DeepOrange/Purple | 3.16 | 4.04 | 4.84 | 3.09 |
| Dark, DeepOrange/Purple | 1.83 | 3.34 | 3.34 | 3.41 |

The current-day number is small bold text at the reference size, so use the
small-text target; the Dark failures are below even 3:1. Of the 19 palette
families, day numbers fall below 4.5:1 in 15 Light/19 Dark cases; selected icons
fall below 3:1 in 10 Light/13 Dark cases; full-fill Undo text falls below 4.5:1
in 4 Light/18 Dark cases. These are component-rendering observations, not reports
of a phone shopping incident. The stock Qt green highlighted button also has low
white-on-fill contrast; simply removing the custom shift does not solve the role
pairing generally.

Undo was also rendered over all ten backgrounds, both themes, at full, half and
empty progress. Nine points across the message area were sampled per frame (60
frames). With default Green, the full fill is 10.49:1 in Light and 1.43:1 in Dark.
Once empty, the measured ranges were 7.86–10.41:1 in Light and 5.77–9.08:1 in
Dark for these fixtures. Half fill exposes both contrast conditions at once.
Thus the new artwork and uncovered transparency are not the cause of the default
Dark Undo failure; the bright opaque fill paired with white is.

System resolved to the corresponding explicit theme in the probe. It uses the
documented application-local [QStyleHints color-scheme override](https://doc.qt.io/qt-6/qstylehints.html#colorScheme-prop),
not a change to Windows OS settings or an Android system-theme event. Current
helpers correctly test resolved `Material.theme`, not raw `Theme.theme`.

## Recommended follow-up, preserving the vivid design

1. **UI-025:** give filled primary/accent surfaces a contrasting foreground or
   choose a compatible same-family fill tone. Keep the current-day name's useful
   Dark primary tone; fix its circle's text pairing separately. For selected
   buttons, a darker icon can preserve the bright fill. Undo needs an explicit
   tradeoff: UI-024 intentionally matches normal TextItem foregrounds, and the
   moving fill exposes two surfaces. A compatible fill tone can preserve that
   foreground policy without per-pixel text-color switching. Do not silently
   undo the accepted foreground policy or add duplicate clipped labels as a
   review cleanup.
2. **UI-026:** separate readable accent ink/focus treatment from the vivid accent
   fill where necessary. Consider a suitable same-family ink shade or a
   contrasting outline for meaningful slider/focus cues. Retain picker swatches
   and decorative fills as the user's selected vivid color. Do not require a
   broad muted palette or reduce every accent use to one color value.
3. Continue UX-002 for action-color meaning, then UX-003 for the remaining custom
   component/state audit, reusing these measurements instead of repeating it.

Each corrective ticket requires a failing-before/passing-after regression at the
real rendered trigger, including Android coverage where relevant. No correction
is implemented or authorized by this review alone. A small local rule/helper is
preferable to a generalized design-system framework.

## Reproduction and evidence

Run the review probe explicitly with the built Windows test executable; normal
QML suites are unchanged. It uses the existing in-memory database and temporary
QSettings harness, with no personal app data:

```powershell
New-Item -ItemType Directory -Path out/ux001 -Force | Out-Null
$env:PATH = 'C:/Qt/6.12.0/msvc2022_64/bin;' + $env:PATH
$env:QT_QUICK_BACKEND = 'rhi'
$env:QSG_RHI_BACKEND = 'd3d11'
$env:QSG_RHI_PREFER_SOFTWARE_RENDERER = '1'
$env:QT_FORCE_STDERR_LOGGING = '1'
Push-Location out/ux001
try {
    & ../windows-agent/qshopper_ui_tests.exe -input ../../reviews/UX-001 -import ../windows-agent -platform windows -o native.txt,txt
} finally {
    Pop-Location
}
```

`UX001_DATA` and `UX001_UNDERLAY` JSON lines contain the measurements; PNG files
contain the component frames. Retained data and representative native frames are
under [UX-001/](UX-001/). The final native repeat was blocked when Windows exposed
only a `WinDisc` screen reporting a negative physical density (-4920 px/mm).
The probe now rejects invalid density and out-of-bounds samples immediately.
Earlier valid native collection (26 passing records) and the separate corrected
whole-scene popup collection remain the native evidence; invalid reruns are not
used. Final probe validation is repeated offscreen with `QT_QUICK_BACKEND=software`,
`QT_QPA_FONTDIR=C:/Windows/Fonts` and `-platform offscreen`, which uses valid density.
Offscreen does not implement the Dark system-scheme override, so its supported
rerun explicitly selects `ColorRoleReview::test_review:Light`,
`ColorRoleReview::test_review:Dark` and `ColorRoleReview::test_underlay`; the two
System rows remain native-only evidence. The unsupported full offscreen attempt
is recorded as 25 passed/1 failed, not hidden or called a System success.
Those palette/composition measurements are not additional native typography proof.
The final supported offscreen run passes 24 records (two palette-mode rows,
twenty underlay rows and setup/cleanup), collecting 46 palette records and twenty
underlay records. Its resolved primary/accent, reference Qt colors, foregrounds
and swatches match the corresponding earlier native data exactly.
Rendered background/popup samples are kept separately: the final production
drawer panel and software rasterization do not reproduce every earlier fixture
composite. For example, the final Light selected Green popup label measures
1.04:1 rather than the native fixture's 1.28:1; both expose the same low-contrast
ink problem. Exact ratios above are the retained native observations.
Passing probe records mean collection/layout/theme checks
succeeded; they do **not** mean the recorded contrast failures passed accessibility
targets. No application behavior changed, so no full app rebuild, general-suite
rerun, APK rebuild or Android install is claimed for this review. Android native
contrast, actual OS-theme events, outdoor viewing, color-vision simulations and
all press/disabled/focus states remain beyond this evidence. This review does
not reopen resolved System drawer or Undo foreground-role tickets.
