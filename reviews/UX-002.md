# UX-002 — Swipe action colors and color-vision accessibility

Reviewed 2026-11-06 against `d944dc9`, Qt 6.12.0 MSVC 2022 x64.
This is a review: no application colors, gestures or dependencies changed.

**Recommendation: keep red for deletion and green for shopping check/uncheck,
keep the existing icon/state cues, and improve the Light-theme swipe icon contrast
under UI-028. Do not add another color picker or a separate color-blind theme.**

Changing red/green to another pair would not remove the need for visible shapes
and adequate contrast. The current semantics are reasonable; the foreground
pairing needs attention before the palette needs replacement.

## What Android does

Android's [accessibility principles](https://developer.android.com/guide/topics/ui/accessibility/principles#use-cues-other-than-color)
recommend distinguishing actions through shape, text or other cues alongside
color. [Its mobile color guidance](https://developer.android.com/design/ui/mobile/guides/styles/color)
specifically flags red/green distinctions as difficult for some users, and calls
for consistent meanings and contrast. It supports expressive colors. There is no
single replacement hue pair that makes every interface accessible.

For users, Android provides [color correction and grayscale](https://support.google.com/accessibility/answer/11183305?hl=en):
Settings → Accessibility → Color and motion → Color correction, then choose the
appropriate correction mode. The exact settings/navigation can vary by device.
These display features complement an accessible app; they do not excuse an app
whose only distinction is red versus green.

For developers, [Simulate color space](https://developer.android.com/studio/debug/dev-options#hardware)
offers monochromacy, deuteranomaly, protanomaly and tritanomaly previews. This is
different from the user's correction setting. Android documents that screenshots
taken with the simulator enabled appear in normal colors. Therefore an ordinary
ADB screenshot cannot establish the simulated on-screen appearance. A later
Android check must observe the live display or use a separately validated capture
of its final displayed output; restore the user's original settings afterward.

[WCAG's use-of-color explanation](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
likewise supports additional visible shape/state cues. For the meaningful bin/cart
graphics, use [3:1 against adjacent backgrounds](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
as the review target. Measure nominal foreground colors against actual composed
backgrounds, rather than treating antialiased edge pixels as the intended ink.
This review does not constitute whole-app accessibility certification.

## Actual QShopper roles

`ShopView.qml` instantiates `TextDelegate` and owns the result of `onSwiped`.
`TextDelegate.qml` paints the exposed feedback. `IconChoser` selects the loaded
`CartInIcon`, `CartOutIcon` or `TrashIcon`; their shared `ArrowIcon` supplies the
animated arrow and clipping. `TextIcon` supplies the body foreground.

| Mode/state | Right swipe | Left swipe |
| --- | --- | --- |
| Shopping, unchecked | Green + cart/entering arrow; check | Green + mirrored cart/entering arrow; check |
| Shopping, checked | Green + cart/leaving arrow; uncheck | Green + mirrored cart/leaving arrow; uncheck |
| Edit, unchecked | Red + bin/arrow; delete | Green + cart/entering arrow; check |
| Edit, checked | Red + bin/arrow; delete | Green + mirrored cart/leaving arrow; uncheck |

Both directions toggle check state except edit-mode right swipe, which deletes.
Do not infer action solely from swipe direction. The application uses fixed
Material Red500/Green500 at 0.8 opacity while revealing feedback; these are not
the user-selected primary/accent or UX-001's A400/A200 shade shift.

The bin/cart silhouettes distinguish destructive from shopping actions without
requiring red/green recognition. Checked entries also have persistent strikeout,
inverse surfaces and their position in the checked group. The cart arrow points
into/out of the basket during the animation. In the settled preview, the outgoing
arrow is clipped away by design, so it is not an always-visible static distinction.
Do not claim the moving arrow alone establishes recognizability for every user.

Red as a chosen accent may also appear on ordinary focus/selection controls. This
does not make those actions destructive: their icon/context distinguishes them.
Replacing semantic swipe colors with arbitrary primary/accent choices would make
action meanings less predictable. Wider custom-state/focus evaluation remains
UX-003; this review does not reopen the resolved UI-025/UI-026 fixes.

## Rendered observations

The explicit [review probe](UX-002/tst_actioncolors.qml) uses production delegates,
font and images at preview scale 2. It covers eight mode/check/direction states
over two actual backgrounds in Light/Dark: 32 settled state measurements. It also
captures idle and moving states. Meaningful cart/bin bodies are sampled at opaque
glyph cores, with the arrows hidden only for the measurement pass, then the entire
icon hidden to capture the exact background at the same locations. Displayed
frames retain the real arrow animation and icon geometry.

Final collection uses a **native Windows window with Qt Quick's software
renderer**, not D3D11 and not Android. Six collection/readiness records pass;
that means collection succeeded, not that all contrast targets passed.

| Appearance/action | Minimum body contrast in sampled frames | Range of per-state median contrast |
| --- | ---: | ---: |
| Light check | 2.274:1 | 2.806–3.405:1 |
| Light uncheck | 2.269:1 | 2.697–3.263:1 |
| Light delete | 2.993:1 | 3.521–4.497:1 |
| Dark check | 4.354:1 | 4.906–5.954:1 |
| Dark uncheck | 4.430:1 | 5.119–6.195:1 |
| Dark delete | 3.494:1 | 3.715–4.744:1 |

The Light cart foreground is `#fffbfe`; Dark uses `#1c1b1f`. Because the strip is
translucent, photo detail changes the adjacent color and the contrast across one
glyph. The Light cart issue is substantial enough to record **UI-028** separately.
The Light bin's 2.993 minimum is a narrow edge case, not proof that every delete
frame is unclear. Include it when testing the full foreground/arrow pair, with
rendered-color rounding margin. No Android incident or whole-app WCAG failure is
asserted from these component samples.

### Color-vision previews

The [comparison](UX-002/comparison.png) applies grayscale and three full-severity
model transforms to the rendered frames. The [analysis script](UX-002/analyze_frames.py)
linearizes sRGB, applies the severity-100 Machado/Oliveira/Fernandes matrices,
clips out-of-gamut values, and re-encodes sRGB. Matrix data were checked against
the [colorspacious implementation](https://raw.githubusercontent.com/njsmith/colorspacious/master/colorspacious/cvd.py),
which publishes the model's supplementary matrices; the original research is
[Machado et al. (2009)](https://doi.org/10.1109/TVCG.2009.113).
These are offline model previews, not Android simulator/correction output, and
do not represent every individual's perception or all intermediate severities.

For illustration, the nominal Red500/Green500 pair becomes:

| Preview | Red | Green |
| --- | --- | --- |
| Original | `#f44336` | `#4caf50` |
| Grayscale, equal RGB channels from luminance | `#858585` | `#9b9b9b` |
| Protanopia model | `#786c33` | `#b2a047` |
| Deuteranopia model | `#a4932e` | `#a59857` |
| Tritanopia model | `#ff0042` | `#3bab9a` |

The deuteranopia preview makes these hues much closer; the bin versus cart shapes
remain the intended action distinction. A transform preserves geometry, but it
does not guarantee the shapes remain easy to recognize at every contrast/size.
The figure is a visual review aid, not an automated recognition test or a new
WCAG threshold on simulated colors. The rendered translucent strips differ from
these nominal swatches because their photos contribute to the composite.

## Alternatives and decision

| Option | Assessment |
| --- | --- |
| Keep red/green plus visible icon/state cues | Recommended. Familiar deletion cue; preserves established gestures and visual character. Correct the faint Light icon pairing |
| Blue/orange or another pair | Could separate better for some red–green deficiencies, but is not universal, changes learned meaning and still needs shape/contrast |
| Derive both actions from primary/accent | Avoid. Users can choose the same or similar families; semantic meanings would change with customization |
| Add a separate color-blind theme/picker | Not justified. More combinations to maintain while leaving icon recognition/contrast as app responsibilities. Preserve system correction support |
| Add more colors for check versus uncheck | Not necessary from this evidence. Existing state/strikeout and animated arrow already supply non-color context; assess clarity with users before adding semantics |

Keep the 19 primary/accent choices and System/Light/Dark. Future UI-028 work should
compare a compatible foreground pair, same-hue feedback tone, or local contrast
backing, with the smallest change that preserves both the cart/bin body and its
arrow. A black body alone is not a complete proposal: the Light arrow is currently
dark too and could merge into it. Preserve the deliberate pullback gestures,
reference dimensions, inverse checked rows and existing Undo.

Analysis requires NumPy and Pillow. The retained measurement JSON contains all
32 states, actual core counts, contrast ranges, icon bounds, effective opacity
and outgoing-arrow visibility. Retained normal frames and the comparison are
linked below. Full generated normal/simulated frames remain under ignored
`out/ux002/`; do not present them as Android screen captures.

D3D11 WARP attempts for this new probe abort with Qt's
`opacity >= 0 && opacity <= 1` assertion (exit `-1073740791`). The ordinary native
Undo control still passes three records. Although the raw swipe ratio exceeds 1,
the effective Item opacity in the software collection is already clamped to 1.
Neither assigning opacity 1 on probe instances nor clamping the opacity source
in a temporary local delegate copy prevents this probe's RHI assertion. Therefore
its cause is **unresolved**; it is not recorded as a confirmed application defect
or attributed to the ratio binding. Logs/temporary experiments are in
`out/ux002/`. The initial offscreen trial also had a probe-only mirrored-bounds
error; the final probe measures mapped rectangles correctly. Its failed samples
are not retained as evidence.

Remaining checks: actual Android held-swipe rendering over representative images,
live system correction/simulator observation, outdoor use, intermediate animation
phases and reduced-motion behavior, and recognition by users with color-vision
differences. Only explicit Light/Dark were rendered here; System mode resolution
was not independently exercised by this probe. Prior UI-025–UI-027 platform
results remain their own evidence, not additional UX-002 coverage. No application
code changed, so no APK rebuild or full regression-suite rerun is claimed.
