# UX-005 — Undo during post-reset cleanup

Selected 2026-11-07 for unattended implementation, alongside UX-003.
Baseline `c632dd3`; this intentionally replaces UI-023's accepted original batch
policy. It does not reopen its resolved timing, reachability or color defects.

## Outcome and policy

Use one Undo step per user deletion action. One swipe is one item. Each explicit
Remove checked or Clear list action remains one coherent bulk step. One tap on
the existing bar restores the latest action; further taps restore earlier ones
in reverse order. The existing message identifies the next action to undo.

Keep one shared 15-second window, restarted by each new deletion. Undo does not
restart it. Expiry discards every pending step, and undoing the last step hides
the bar/stops its clock. Drawer/app-inactive pauses and current-list/process/
successful-reload boundaries are unchanged. New deletion after Undo discards the
undone future while preserving older pending actions. Each recognized tap is one
step, including rapid distinct taps; no new history screen, extra button,
lockout, per-item clock or persistent recovery archive is introduced.

Example: after Reset, delete Birthday candles, then Gift wrap, then mistakenly
Milk. One Undo returns Milk alongside Bread; candles and wrap stay removed.
Further Undo taps deliberately recover Gift wrap, then Birthday candles. Saved
identities, check flags and the shopper's post-reset order remain intact.

## Alternatives

The original restore-all batch is useful when an entire cleanup was mistaken,
but reverses intended work when only one removal was wrong. Latest-action-only
recovery hides an older mistake as soon as another deletion occurs. A per-action
stack supports both without another UI: only deliberate further taps restore
older actions. Accidental extra taps can still restore another item, so the
message and returned-row animation remain important; real one-handed shopping
acceptance complements the automated tap sequence.

Separate item timers and resetting the clock on every Undo add policy/state that
the reported use case does not require. Retaining the shared clock is the
smallest change to an already accepted interaction. Bulk operations should stay
coherent because one explicit action can remove several items.

## Implementation

Model already owns QUndoStack, and every remove operation already constructs a
command. Remove UndoRemove's `id()`/`mergeWith()` overrides so Qt's default
non-merging behavior preserves these commands separately. No new history engine
or changes to Model/UndoBar timing code are needed. Bulk commands already hold
multiple records. Existing UUID/neighbor restoration preserves surviving/new
items and pending edits.

Qt documents that the base command ID disables compression and that pushing a
new command after Undo discards the undone future. These are the framework's
existing semantics, covered here by observable regression tests.
[QUndoCommand](https://doc.qt.io/qt-6/qundocommand.html#id),
[QUndoStack::push](https://doc.qt.io/qt-6/qundostack.html#push).

## Evidence

Original model behavior fails four new cases: post-reset individual recovery,
deletion after Undo, and separate Remove checked/Clear list steps. A real QML
swipe sequence exposes the merged count rather than the latest item. Native
Android checks, drawer Reset, three cleanup swipes and one bar tap restore all
four original rows instead of only Milk/Bread. Logs are linked in the ticket.

After the change, all 104 model records pass, including existing pending-editor,
read-only, mutation, UUID, ordering and persistence cases. The QML sequence uses
actual swipe gestures and repeated whole-bar taps and verifies that Undo does
not extend the deadline. Another case expires multiple pending actions.

Native Android cleanup passes six checks, including each individual restoration
and a cold restart. The native recovery script passes 24 checks across both
themes: offscreen editor, scrolling, two separate Undo taps after new entry,
retained Gboard, real expiry and paused background/resume. No microphone or
physical-device installation is used. All 17 combined Windows suites pass (1,622 records), both C++ analyzers
pass all seven translation units, and both APK package/signature checks pass.
Detailed rendering/package results are recorded in [UX-005](../tickets/UX-005.json).

An intermediate native driver requested an idle UI dump during the animated
countdown and failed to obtain it. The final script retains the established
rendered-bar approach; multiple-pending-action expiry is covered by the normal
QML regression, while native expiry exercises the actual 15-second window.

Physical store use, accidental-tap frequency and dictation are not established
by emulator automation. The user tested the APK and accepted the fix on 2026-11-07, requesting closure
and a commit. This acceptance does not assert that every broader QA scenario was exercised.
